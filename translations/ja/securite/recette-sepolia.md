# Sepolia での手動テスト計画

このページは、ウォレットを持つ人が Sepolia テストネットワーク上で**手作業で実行できるチェックリスト**です。各ケースには `T-01` 形式の固定番号が付いており、報告で引用できます。

> **始める前に。** この計画は新バージョンを対象とします。リポジトリの公開マニフェストは LP 手数料 `100` の**稼働中の** Sepolia デプロイを記述しており、この計画はそれに適用されます。テスト対象の版に該当しないケースは「版の対象範囲外」と記録し、決して「失敗」とは記録しません。

記載する値は、`contracts/src/` にある新バージョンのコードと、2026 年 9 月 14 日の設計上の決定に基づきます。確認できなかった動作には**「テスト時に要確認」**と記しています。

## この計画の使い方

各セクションは、ケースを 6 列の表で示します。最後の 2 列は受入検証中に記入します。

| 列 | 記入内容 |
| --- | --- |
| ケース | 固定の識別子、`T-01` から `T-110` |
| 前提条件 | 開始前に満たされているべきこと |
| 手順 | 実行する操作（順番どおり） |
| 想定結果 | コードと決定が想定すること |
| 観察結果 | 実際に起きたこと。取引 hash または読取りブロックを添える |
| 重大度 | 適合なら空欄。そうでなければブロッカー、重大、軽微、外観のいずれか |

| 重大度 | 基準 |
| --- | --- |
| ブロッカー | 資金の損失または凍結、税の未徴収、買い壁の喪失、元本からの報酬支払い |
| 重大 | ソースに反する動作、あるべき拒否の欠如、表示される数値の誤り |
| 軽微 | チェーンに影響しない表示の差異、不正確なメッセージ |
| 外観 | 文字表記、レイアウト、ラベル |

**拒否ケースのとおりに拒否された取引は成功です**。hash は取引が提出されたことを示すだけで、成功はレシートでのみ判断できます。

**一部のケースは画面を通しません。** 現在のソースでは、dapp は稼働中のバージョンの ABI を読んでおり、exact-output 注文も `claimTeam()` も買い壁の詳細な読取りも提供していません。これらのケースには「直接呼出し」と記しており、テスト対象デプロイのマニフェストにあるアドレスに対して、コントラクト呼出しツールで実行します。

## 1. 準備

最初のスワップの**前に**、次の項目を記録します。以降のすべての比較の基準になります。

- ネットワーク：Sepolia、チェーン ID `11155111`。
- テスト対象デプロイのアドレス（マニフェストから読む）：トークン、フック、PoolManager、`poolId`、ルーター、Lens、V2 レジストリ、Vault、ローンチャー。ローンチパッドの追加後は、ガバナンス Vault と Forge。**秘密鍵をメモにコピーしないでください。**

- 初期状態：Lens の `snapshot()`、フックの `band()`、トークンの `totalSupply()` と `totalBurned()`、`pendingFloorEth`、`pendingAbsorbedTokens`、`wallCount()`、`activeWallCount()`、`teamAccrued`、`teamPaidCumulative`、Vault の `rewardReserve()`、および読取りの**ブロック番号**。

## 2. ローンチとバンド

プールの初期化時、フックは**預入れの全額**を、`BAND_SALT` で識別される単一のポジション `[minUsableTick, tickUpper]` に配置します。`tickUpper` は開始 tick を間隔に合わせて切り下げた値なので、ポジションには CUBIT しか含まれません。フックは `MIN_POOL_SUPPLY`（供給量の 80 %）未満の預入れを拒否し、丸めによる端数をバーンします。

完全なローンチでは、供給量の 20 % も Vault の準備金に入れ、同じトランザクションで 0.1 ETH の購入を行います。

## 3. 購入と売却の手順

ルーターは `swapExactIn(key, zeroForOne, amountIn, amountOutMin, recipient, deadline)` と `swapExactOut(key, zeroForOne, amountOut, amountInMax, recipient, deadline)` を公開しています。`zeroForOne = true` は ETH で CUBIT を購入します。

**dapp の現在のソースでは、画面は exact-input しか使いません。** 利用者は常に支払う金額を入力し、受取数量は読取り専用の欄です。したがって exact-output の手順は、ルーターへの直接呼出しでテストする必要があります。

購入は `msg.value` でネイティブ ETH を送ります。売却は value ゼロで送り、ルーターに対する CUBIT の **ERC-20 承認**が必要です。画面は**ちょうどその金額**の承認を求め、無制限の承認は求めないため、より大きな売却には新しい承認が必要です。

ルーターは部分約定を拒否します。全額消費されない exact-input は `IncompleteInput`、全量提供されない exact-output は `InsufficientOutput` になります。税は要求額に基づいて計算されるため、取り消しは利用者を保護します。

dapp のソースから読んだ画面設定（受入検証で確認する）：スリッページ許容度は**既定値 1.0 %**、入力は**小数 2 桁**までかつ `0` から `99.99` の範囲。最低受取量は整数で計算し、**wei 単位で切り上げ**。見積もりは **30 秒間有効**。オンチェーン期限 = チェーンの timestamp **+ 120 秒 − 見積もりの経過時間**。

| --- | --- | --- | --- | --- | --- |
| T-17 | ETH 残高が十分 | 少額を購入する（例：0.001 ETH） | 成功レシート。CUBIT が入金される。`BuyTaxed` イベントが発行される |  |  |
| T-18 | ETH 残高が多い | 高額を購入する | 成功レシート。価格影響は見積もりに現れ、税率には現れない |  |  |
| T-19 | CUBIT を保有 | 承認してから売却する | 別々の 2 取引。手取り ETH を受け取る。`SellTaxed` が発行される |  |  |
| T-20 | 前回の売却が確定 | 前回**より大きい**額を売却する | 新しい承認が求められる。承認はちょうどその金額に対するものだった |  |  |
| T-21 | スワップ画面を開いている | 何も触らずに提示された許容度を読む | 既定値 **1.0 %** |  |  |

## 4. 税と会計

| 操作 | 基準 | 配分 |
| --- | --- | --- |
| 購入 | ETH 総額部分の 3 % | 100 % チーム分。買い壁への配分は明示的にゼロ |
| 売却 | 総出力 ETH の 15 % | 12 % を買い壁へ、3 % をチームへ |

exact-input では、購入税は渡された金額に**含まれ**、wei 単位で切り上げられます。exact-output では、プール部分の上に加算されるため、合計に対する税の割合は 3 % のままです。

exact-output の売却では、税は `ceil(sortie × 1500 / 8500)` です。プールは要求された出力**に加えて**税を生み出します。exact-input の売却では、税は `ceil(brut × 15 %)` です。配分ではチーム分が切り捨てられ、**wei 単位の残りはすべて買い壁に入ります**。

dapp の現在のソースでは、画面はスワップを許可する前にこれらの税率をチェーン上で読むことを要求します。確認されるまで、ボタンは待機状態のままです。

| ケース | 前提条件 | 手順 | 想定結果 | 観察結果 | 重大度 |
| --- | --- | --- | --- | --- | --- |
| T-34 | 購入確定 | `BuyTaxed(ethIn, toFloor, toTeam)` を読む | `toFloor` はゼロ。`toTeam` は総入力の 3 %（wei 単位で切り上げ） |  |  |
| T-35 | 購入確定 | 前後の `teamAccrued` を比較する | 増加額はチーム分と等しい |  |  |
| T-36 | 売却確定 | `SellTaxed(ethOut, toFloor, toTeam)` を読む | `toFloor + toTeam` は総額の 15 %。`toTeam` は総額の 3 %。合計は wei 単位まで正確 |  |  |
| T-37 | `teamAccrued` がゼロでない、直接呼出し | 任意のアカウントから `claimTeam()` を呼ぶ | 資金は固定されたチームアドレスへ送られる。`TeamPaid(amount, cumulative)` が発行される。`teamAccrued` はゼロに戻る |  |  |
| T-38 | `teamAccrued` がゼロ、直接呼出し | `claimTeam()` を呼ぶ | 呼出しはエラーにならず、何も送金しない |  |  |
| T-39 | 同額の購入と売却を 1 回ずつ | gas を除き、開始時と終了時の ETH を比較する | 残る比率は `0.97 × 0.85 = 0.8245` に近い。差は LP 手数料、価格影響、丸めで説明できる |  |  |
| T-40 | 大きさが大きく異なる 2 回の売却 | 総額に対する税の割合を比較する | どちらも税率は 15 %。段階や免除はない |  |  |

## 5. 自動買い壁

exact-input でも exact-output でも、売却のたびにフックは `_collectCrossedWalls()` を呼び、次に `_placeWall()` を呼びます。まず価格が完全に通過したすべての買い壁を近いものから遠いものへ順に空にし、次にすべての待機中の ETH を目標 `0.4 × prix courant + 0.6 × prix de lancement` に配置します。目標は売却**後**の価格で計算し、tick に丸めます。ローンチ価格以下のようにこの目標がプールの tick より厳密に上にない場合は、買い壁を現在価格の 1 % 下に配置します。

空にされた買い壁は、その CUBIT を `pendingAbsorbedTokens` に加え、残りの ETH（手数料と端数）を `pendingFloorEth` に戻します。一部消費されただけの買い壁はその場にとどまります。流動性を作るには小さすぎる金額と、価格が tick 範囲の最上端にあり価格の下に買い壁を置く余地がない極端な場合だけが、資金を `pendingFloorEth` で待機させます。これを理由に売却が拒否されることは決してありません。その後、CUBIT ルーターが try/catch の中で `deliverAbsorbed()` を呼び出します。

Lens の参照値 `floorPrice()` は**最後に資金供給された買い壁**を示し、全体の最低価格ではありません。通過される買い壁 1 つにつき約 185 000 gas かかるため、1 トランザクションの上限 16 777 216 gas の範囲内で 1 回の売却が通過できる買い壁は最大で約 88 です。

| --- | --- | --- | --- | --- | --- |
| T-41 | 価格がローンチ価格より上 | 売却し、買い壁を読む | `WallFunded(id, lower, addedEth, liquidity)` が発行される。丸めを除き、売却の 12 % を含む待機中の ETH で目標 tick に買い壁が作られるか厚くなる。`pendingFloorEth` には配置されなかった残余だけが残る |  |  |

## 6. mCUBIT Vault

Vault は `rewardReserve` からのみ引き出される **CUBIT 建て**の報酬を支払います。報酬は `DAILY_REWARD_BPS = 300`、すなわち 24 時間の期間（`REWARD_PERIOD`）あたり預入額の 3 % で、比例計算され、**1 期間分が上限**です。それを超えた分は失われます。準備金の残高を超えることはなく、元本から支払われることもありません。

各預入れは、ウォレットの全ポジションについて **24 時間**のロック（`LOCK_DURATION`）を再開します。期限前の引出しは `Locked` で拒否されます。預入れ、引出し、請求はまず獲得済みの報酬を支払い、期間を新たに開始します。どのアカウントも `fundRewardReserve(amount)` で準備金に資金を追加できます。期限はブラウザーの時計ではなく、チェーンの timestamp で判断します。

報酬は **CUBIT のみ**で、`claimCubit()` で請求します。Vault は WETH 報酬の関数を一切公開していません。

| ケース | 前提条件 | 手順 | 想定結果 | 観察結果 | 重大度 |
| --- | --- | --- | --- | --- | --- |
| T-53 | Vault が利用可能、CUBIT を保有 | 承認してから預け入れる | `Staked(user, amount, unlockAt)` が発行される。`unlockAt` はブロックの timestamp + 24 時間 |  |  |
| T-54 | 既存のポジション | 期限前に再度預け入れる | ロックは**ポジション全体について再開**する。獲得済み報酬がゼロでなければ `CubitRewardClaimed` とともに支払われ、期間が新たに始まる |  |  |
| T-55 | ロック期間中 | 引出しを要求する | `Locked` で拒否 |  |  |
| T-56 | ロック期限切れ | 預入れの一部を引き出す | 一部引出しが受け付けられる。`Withdrawn` が発行される。獲得済み報酬が先に支払われる。残りは預け入れたまま |  |  |
| T-57 | 1 000 CUBIT を預入れ、準備金は十分 | 12 時間後、次に 24 時間後に `pendingCubit` を読む | 約 15 CUBIT、次に 30 CUBIT |  |  |

## 7. ローンチパッドのガバナンス Vault

ガバナンス Vault は、Forge のローンチ手数料（ETH）と、Forge の子市場の買い壁が吸収したトークンを受け取ります。**各預入れは、それぞれの受領時から 30 日間ロックされます**（`LOCK_DURATION`）。請求できるのは**デプロイヤーだけ**で、この権利は恒久的で譲渡できません。期日を過ぎたロットのみを古い順に請求できます。ETH はキー `ETH()`（ゼロアドレス）で記帳されます。受入検証の前にテスト対象デプロイの ABI を読み直してください。デプロイヤーは `extendLock` で現在と将来のすべての預入れのロックを延長でき、`lockExtension()` は増えるだけで各期日に加算されます。

子市場の買い壁からの自動送付は T-52 で、ローンチ手数料の預入れは T-81 で確認します。T-67 から T-73 のケースでは直接呼出しでテスト用トークンを預け入れ、T-108 では手数料の ETH を請求します。

| ケース | 前提条件 | 手順 | 想定結果 | 観察結果 | 重大度 |
| --- | --- | --- | --- | --- | --- |
| T-67 | テスト用トークン、直接呼出し | 承認してから `deposit(token, amount)` を呼ぶ | `Deposited(token, from, amount, unlockAt)` が発行される。`unlockAt` はブロックの timestamp + 30 日。`held(token)` が同額増える |  |  |
| T-68 | 30 日未満の預入れ | デプロイヤーから `claim(token, n)` を呼ぶ | `NothingToClaim` で拒否 |  |  |
| T-69 | ロック解除済みのロット | 別のアカウントから `claim(token, n)` を呼ぶ | `NotDeployer` で拒否 |  |  |
| T-70 | 7 日間、毎日 1 回の預入れ | 最初の預入れから 30 日目以降、毎日請求する | 1 日に 1 ロットずつ古い順に払い出される。最後のロットは 7 回目の預入れの 30 日後。請求のたびに `Claimed(token, amount, tranches)` |  |  |
| T-71 | ロック解除済みのロットが複数 | `claim(token, 1)` を呼ぶ | 支払われるのは 1 ロットだけ。次のロットは請求可能なまま |  |  |
| T-72 | 単純な送金で送られたトークン | `lockUntracked(token)` を呼び、新たな送金なしに再度呼ぶ | 最初の呼出しから 30 日間ロックされる新しいロット。2 回目の呼出しは `NothingToLock` で拒否 |  |  |
| T-73 | ロック中とロック解除済みのロット | `claimable(token)` と `locked(token)` を読む | 請求可能額とロック額の合計が `held(token)` に等しい |  |  |
| T-108 | T-81 のローンチ手数料の預入れから 30 日超 | 別のアカウントから、次にデプロイヤーから `claim(address(0), 1)` を呼び出す | まず `NotDeployer` で拒否され、次に ETH がデプロイヤーに支払われる。`Claimed(address(0), amount, 1)` が発行される。`held(address(0))` が支払額だけ減る |  |  |
| T-109 | ロック中のロット | 別のアカウントから、次にデプロイヤーから `extendLock(extra)` を呼び出す | まず `NotDeployer` で拒否され、次に `LockExtended(extra, lockExtension)` が発行される。`tranche(token, i)` で読む各期日が `extra` だけ後ろにずれる。ロックを短縮する関数はない |  |  |

## 8. Forge

Forge は将来のリリースとして紹介する公開ローンチパッドです。CUBIT のローンチには含まれず、後からガバナンス Vault とともに追加されます。ローンチパッドの追加後にそのアドレスを記録してください。

どのアカウントも正確な手数料を支払えば子市場をローンチできます。Forge の子市場は供給量の全額を自身のバンドに預け入れ、Forge は構築時にガバナンス Vault のアドレスを受け取り、各ローンチは 0.005 ETH の手数料をこの Vault に支払い、Vault がそれを保持します。ローンチした側に返金されることはありません。デプロイ salt はローンチするアカウントに結び付けられます。

| ケース | 前提条件 | 手順 | 想定結果 | 観察結果 | 重大度 |
| --- | --- | --- | --- | --- | --- |
| T-81 | Forge が利用可能、任意のアカウント | 0.005 ETH の正確な手数料で子市場をローンチする | `ChildLaunched(token, hook, launcher, team, fee)` が発行される。子市場の `BandBootstrapped` は、丸めを除き供給量の全額に等しい預入れを示す。ガバナンス Vault が `Deposited(address(0), forge, fee, unlockAt)` を発行し、`unlockAt` はブロックのタイムスタンプに 30 日と延長分を加えた値。親フックの `pendingFloorEth` は変わらない |  |  |
| T-82 | Forge が利用可能 | 誤った value、空の名前、ゼロのチーム、または別のテンプレートでローンチを試みる | 拒否：`wrong launch fee`、`invalid name`、`invalid team`、または `template mismatch` |  |  |
| T-110 | 別のアカウントに見られたローンチの salt | 同じ salt で二つ目のアカウントからローンチする | 最初のローンチのアドレスは奪われない。salt はローンチするアカウントに結び付き、フックのアドレスが権限を持たない場合、二つ目のローンチは `child deployment failed` で拒否される |  |  |

## 9. 交換と権限

レジストリの authority は、Vault、ルーター、Lens、Forge の四つの周辺アドレスをいつでも遅延なく交換できます。交換のたびに `ModuleUpdated` が発行され、**`moduleRevision` が増え**、該当する機能（Vault、Momentum、Forge）はチームが再び公開するまで閉じます。ルーターの交換で閉じる機能はありません。登録済みの候補、別のフックや別のトークンに接続された候補、既に stake のある候補は `InvalidModule` で拒否されます。

フックには**管理者がいません**。誰もスワップや買い壁の仕組みを一時停止できません。チームアドレスは恒久的な権限を保持し、チーム分の税を受け取り、レジストリのモジュールを交換してから有効化します。

| ケース | 前提条件 | 手順 | 想定結果 | 観察結果 | 重大度 |
| --- | --- | --- | --- | --- | --- |
| T-83 | 現行 Vault に預入れと準備金がある | Vault を交換する | 預け入れた CUBIT、報酬準備金、期限は**旧 Vault に残る**。資金は移動しない |  |  |
| T-84 | Vault が交換済み | 旧 Vault で請求と引出しを行い、次に預入れを試みる | 請求と引出しは引き続き可能。新しい預入れは `Inactive` で拒否 |  |  |
| T-85 | 登録済みの候補、または stake のある候補 | 交換を試みる | `InvalidModule` で拒否 |  |  |
| T-86 | 交換を実施済み | `moduleRevision()` とイベントを読む。Vault の交換後は新しい Vault への預入れを試す | 改訂が増えている。`ModuleUpdated(module, previous, current, revision)` が一致する。Vault が再び有効化されるまで預入れは `Inactive` で拒否される |  |  |
| T-87 | 旧ルーターに承認を与えている | ルーターを交換し、売却を試みる | 旧承認は新しい spender には有効でない。新しい承認が求められる |  |  |
| T-88 | ルーター交換済み | 旧ルーターでスワップする | スワップは引き続き可能で、フックの税が適用される。dapp は新しいルーターを使う |  |  |
| T-89 | 直接呼出し | デプロイされたフックの ABI を確認する | スワップや買い壁の仕組みを停止できる関数はない。フックには管理者がいない |  |  |
| T-90 | 直接呼出し | Lens の `snapshot()` を読み、同じブロックで買い壁のページを読む | snapshot に含まれるのは、市場、バンド、買い壁、会計のフィールド、総供給量、報酬準備金、有効な買い壁の数、読取りブロックと最良の買い壁だけで、買い壁の合計は含まれず、その費用は買い壁の数に依存しない。流通供給量は `totalSupply` から買い壁の CUBIT と `rewardReserve` を引いた値で、保有 CUBIT はその供給量から `bandTokens` を引いた値 |  |  |
| T-91 | ローンチ後の任意の時点 | 購入と売却を行う | スワップは通常どおり動作する。どのアカウントもスワップを止められない |  |  |

## 10. 想定される拒否ケース

この表は受入検証全体を通じた参照用です。自動買い壁は売却に拒否を追加しません。買い壁を配置できない場合は資金が待機し、失敗した送付は CUBIT を待機させたままにします。

> **注意点。** dapp の現在のソースでは、コントラクトのエラーは翻訳されていません。オンチェーンの拒否が、表示上切り詰められた生のメッセージとして表示される場合があります。**発生させた拒否ごとに、表示された正確なテキストを記録し**、理解できる内容か判断してください。

| エラー | 発生条件 | アプリが示すべき内容 |
| --- | --- | --- |
| `ExternalLiquidityForbidden` | 第三者による流動性の追加 | 操作不可：プロトコルが唯一の流動性提供者 |
| `SupplyNotDeposited` | 供給量の 80 % 未満の預入れでの初期化 | ローンチ不可、預入れ不足 |
| `Expired` | 取引期限切れ | 見積もりの期限切れ、再計算が必要 |
| `TooLittleReceived(received, minimum)` | 出力が受け付けた最低額を下回る | スリッページ保護が作動 |
| `TooMuchRequested(required, maximum)` | 入力が受け付けた上限を超える | 入力上限の保護が作動 |
| `IncompleteInput` | exact-input が全額消費されない | 利用可能な流動性に対して金額が大きすぎる |
| `InsufficientOutput` | exact-output が全量提供されない | オーダーブックがこの出力を提供できない |
| `InvalidAmount`, `ZeroRecipient`, `WrongValue`, `WrongPool` | 無効な注文パラメーター、または Vault へのゼロ額 | 入力エラーとして表示し、生のコードは出さない |
| `Inactive`, `Locked` | 現行レジストリに接続されていない Vault、または期限前の引出し | モジュール利用不可、またはロック解除日 |
| `NotDeployer`, `NothingToClaim`, `NothingToLock`, `NothingToExtend` | 第三者によるガバナンス Vault への請求や延長、期限前の請求、新しい残高のないロック、ゼロの延長 | 限定された操作、請求するものなし、ロックするものなし、または延長するものなし |
| `NotAuthority`, `InvalidModule` | 第三者による交換要求、または互換性のない候補 | 交換の拒否とその理由 |

アプリ側だけの拒否も記録します：期限切れの見積もり、変更されたスワップ状態、別チェーン上のウォレット、変更されたアカウント、変更されたモジュール改訂、まだ確認されていない税率。
